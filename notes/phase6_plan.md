# Phase 6 plan: explainability and precompute

Written before the full Phase 6 run. Earlier plans still apply; this file adds the Phase 6 rules. If a rule changes, record it in the change log with the reason.

## 1. Goal

Everything the app (Phase 7) needs, computed once from the final model and saved to files, with checks that the explanations are faithful:

- every player's top career comps
- a "why similar" breakdown for each player's top comps
- 2D map coordinates for every season (for the map and career trajectory lines)
- the profile vectors, so the app can apply the lambda slider live

Phase 6 trains nothing and doesn't change any comp. It explains and packages what Phase 5 chose.

## 2. Final model

Seed 2026 of the Phase 5 chosen pipeline:

| Stage | Setting | From |
|---|---|---|
| Season encoder | Phase 3 setting (embedding 32, temperature 0.05, pretraining), the lambda 0 control | `models/phase4/adversary_lambda0.0_s2026.pt` |
| Era removal | Season centring, alpha 0.5 | Phase 4 |
| Career score | Centre 0.25, peak 0.75, lambda 0 (the default; lambda stays a live slider) | Phase 5 |

One seed is used because the app needs one model. Seed 2026 is the one all sanity comps were judged on. `precompute.py` refuses to run if the Phase 5 report's chosen setting doesn't match its constants.

Hold-outs stay excluded until final evaluation. All other players (train, validation and test) are included: Phase 6 computes no metric on test players, it only packages comps for display.

## 3. Why similar

**Method: integrated gradients** (Sundararajan et al., 2017) through the whole pipeline: encoder, season centring, career profile (centre and peak), career score. The score for a pair (A, B) is rebuilt in PyTorch so gradients reach every season's 15 style z-scores.

- For A: walk A's seasons from the baseline (0 = league average in every season) to his real values in 64 midpoint steps, with B fixed, and credit each feature with its share of S(A, B) - S(average, B).
- The same for B with A fixed; average the two.
- Sum over seasons: one number per feature. Positive = this stat makes them more alike than an average player would be.
- The peak seasons are fixed by BPM before the walk (the selection itself isn't differentiable).

**Checks:**

| Check | How | Why |
|---|---|---|
| Completeness | The attributions must add up to the score change they explain. Relative error per pair | The defining property of integrated gradients; a large error means too few steps or a bug |
| Deletion test | On 300 random (player, top-5 comp) pairs: set A's 3 most-credited features to league average and measure the score drop; compare with 3 random features (10 draws) | Faithfulness: if the explanation is right, its top features should matter more than random ones |
| Example pairs | Breakdowns for Jordan/Kobe, Shaq/Howard, Rodman/Reggie Evans, Stockton/Chris Paul, Nash/Mark Price | Human check that the credited stats make basketball sense |

## 4. Map

UMAP on every season's centred embedding: 15 neighbours, min_dist 0.1, cosine metric, random_state 2026. Quality is reported as **trustworthiness** (10 neighbours, a fixed 3,000-season sample): the share of 2D neighbourhoods that are real neighbourhoods. The map is for display only; comps are always computed in the full embedding (feature note, check 6), so trustworthiness is reported, not gated.

## 5. Exports

Written to `exports/` (git-ignored; regenerated by `python src/precompute.py`): `players.json`, `comps.json` (top 10 per player at lambda 0), `why.json` (breakdown for the top 5), `seasons_umap.csv`, `profiles.npz` (centre, peak, spread and the score scales), and `manifest.json` (model provenance, settings, counts, SHA-256 of every file). Whether exports get committed or hosted is a Phase 7 decision.

**Reproducibility:** running `precompute.py` twice must give identical SHA-256 for every export.

## 6. Gate

- This plan is committed before the full run.
- Every player has 10 comps.
- Every player has a why-similar breakdown for his top 5.
- Every season has map coordinates.
- Mean completeness error under 1%.
- Deletion test: the top 3 credited features matter more than 3 random ones on average, and in at least 70% of pairs.
- Two runs give identical export checksums.
- Report (`reports/phase6_explain.md`), notebook and run log committed.
- If a line fails, record it as a finding. Don't change the metric.

A quick run (40 players) on 18 Nov, before these thresholds were written, gave completeness error 0.11% on average and a deletion-test drop of 0.80 (top 3) against 0.22 (random). The thresholds above are the standard ones for these checks, not tuned to that run.
